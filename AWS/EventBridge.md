# Amazon EventBridge

## What is Amazon EventBridge?

Amazon EventBridge is a **serverless event bus service** used to receive, route, and deliver events between AWS services, applications, and external systems.

It allows applications to respond to events without tightly coupling the systems together.

```text
Event Source
     |
     ↓
EventBridge
     |
     ↓
Rule
     |
     ├── Lambda
     ├── SQS
     ├── SNS
     ├── Step Functions
     └── Other AWS Services
```

---

## Why Use EventBridge?

Without EventBridge, applications may need direct integrations:

```text
Application A
      |
      ↓
Application B
```

With EventBridge:

```text
Application A
      |
      ↓
EventBridge
      |
      ↓
Application B
```

This provides **loose coupling** and makes event-driven architectures easier to build.

---

## What is an Event?

An event is a record describing something that happened.

Examples:

* An EC2 instance changes state
* An object is created in S3
* An AWS service performs an action
* A scheduled time is reached
* A custom application generates an event

Conceptually:

```text
Something happens
       ↓
    Event
       ↓
EventBridge
```

---

## Event Bus

An **event bus** receives events and routes them to appropriate targets.

EventBridge provides different types of event buses.

### Default Event Bus

The default event bus receives events generated by AWS services.

Example:

```text
EC2 State Change
      ↓
Default Event Bus
      ↓
Rule
      ↓
Lambda
```

### Custom Event Bus

A custom event bus can be used for application-generated events.

Example:

```text
Sheepeye Application
       ↓
Custom Event Bus
       ↓
Rules
       ↓
Targets
```

### Partner Event Bus

Partner event buses allow events from supported third-party applications and SaaS providers to be integrated with EventBridge.

---

# Rules

An EventBridge **rule** determines which events should be routed to a target.

Example:

```text
Event
  ↓
Rule
  ↓
Target
```

A rule can match events based on their content.

For example:

```text
source = aws.ec2
detail-type = EC2 Instance State-change Notification
state = stopped
```

The rule can then trigger a target.

---

## Event Pattern

An event pattern defines the events that a rule should match.

Conceptual example:

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": {
    "state": ["stopped"]
  }
}
```

This rule could match an EC2 instance entering the `stopped` state.

---

## Targets

A target is the destination that receives a matched event.

Common targets include:

* Lambda
* SQS
* SNS
* Step Functions
* Kinesis
* API destinations
* Other AWS services

Example:

```text
EC2 Event
    ↓
EventBridge Rule
    ↓
Lambda
```

---

# Event-Driven Architecture

EventBridge is commonly used to build **event-driven architectures**.

Instead of applications continuously checking whether something happened, an event can trigger the required action.

```text
Something happens
       ↓
     Event
       ↓
 EventBridge
       ↓
     Rule
       ↓
    Target
```

This can reduce unnecessary polling and application coupling.

---

## Example: EC2 Monitoring

Suppose you want to trigger a Lambda function whenever an EC2 instance stops.

```text
EC2
 |
 | Instance stopped
 ↓
EventBridge
 |
 ↓
Rule
 |
 ↓
Lambda
 |
 ↓
Notification / Remediation
```

The Lambda function could perform an automated action.

---

## Example: Scheduled Events

EventBridge can also trigger targets on a schedule.

Example:

```text
Schedule
   ↓
EventBridge
   ↓
Lambda
```

A Lambda function could be triggered periodically to perform a task.

Examples:

* Daily cleanup
* Scheduled reports
* Periodic maintenance
* Automated checks

---

## EventBridge Scheduler

EventBridge Scheduler is designed specifically for scheduling tasks.

It can invoke supported AWS targets at:

* A specific time
* A recurring interval
* A cron schedule

Example:

```text
Every day at a scheduled time
             ↓
        EventBridge
             ↓
           Lambda
```

For SAA questions, remember that EventBridge supports both **event-driven** and **scheduled** automation.

# EventBridge vs SQS

These services solve different problems.

| Feature                         | EventBridge                                       | SQS                             |
| ------------------------------- | ------------------------------------------------- | ------------------------------- |
| Main purpose                    | Event routing                                     | Message queuing                 |
| Model                           | Event bus                                         | Queue                           |
| Routing based on event patterns | Yes                                               | No                              |
| Buffer workloads                | Not its primary purpose                           | Yes                             |
| Decouple applications           | Yes                                               | Yes                             |
| Consumer processing             | Targets receive events                            | Consumers poll/process messages |
| Dead-letter queues              | Supported for some target delivery configurations | Core queue feature              |

Simple rule:

```text
Need event routing?
       ↓
  EventBridge

Need a queue/buffer?
       ↓
      SQS
```

---

# EventBridge vs SNS

Both can distribute events/messages, but their primary use cases differ.

### SNS

SNS is mainly used for **pub/sub and fan-out**.

```text
SNS
 |
 ├── SQS
 ├── Lambda
 └── Other subscribers
```

### EventBridge

EventBridge focuses on **event routing using event patterns and rules**.

```text
Events
  ↓
EventBridge
  ↓
Rules
  ↓
Different targets
```

Simple rule:

```text
Need simple notification/fan-out?
        ↓
       SNS

Need intelligent event routing?
        ↓
   EventBridge
```

---

# EventBridge and Lambda

Lambda is a common EventBridge target.

```text
Event
  ↓
EventBridge
  ↓
Rule
  ↓
Lambda
```

Example:

An S3-related event occurs → EventBridge matches it → Lambda performs processing.

This allows serverless automation without running a continuously active server.

---

# EventBridge and SQS

EventBridge can send matching events to SQS.

```text
Event
  ↓
EventBridge
  ↓
Rule
  ↓
SQS
  ↓
Worker
```

This combines:

* Event routing from EventBridge
* Buffering and asynchronous processing from SQS

This is useful when the target application should process events asynchronously.

---

# EventBridge and SNS

EventBridge can also route events to SNS.

```text
AWS Event
    ↓
EventBridge
    ↓
Rule
    ↓
SNS
    ↓
Subscribers
```

This can be useful when an event needs to be distributed to multiple subscribers.

---

# EventBridge and CloudTrail

CloudTrail records AWS API activity.

Some CloudTrail events can be delivered to EventBridge.

Example:

```text
AWS API Activity
       ↓
   CloudTrail
       ↓
 EventBridge
       ↓
      Rule
       ↓
    Target
```

This can be used for automated responses to specific API activity.

# EventBridge and CloudWatch

CloudWatch and EventBridge are closely related but have different primary purposes.

### CloudWatch

Mainly focuses on:

* Metrics
* Logs
* Alarms
* Monitoring
* Observability

### EventBridge

Mainly focuses on:

* Events
* Event routing
* Event-driven automation
* Scheduling

Example:

```text
CloudWatch
    ↓
Monitoring / Alarm

EventBridge
    ↓
Event routing / automation
```

# EventBridge Archive and Replay

EventBridge supports event archiving and replay.

Conceptually:

```text
Events
  ↓
Archive
  ↓
Replay
  ↓
Event Bus
```

This can be useful for testing or recovering/reprocessing events.

---

# EventBridge Security

EventBridge uses AWS IAM to control access.

Permissions can control who can:

* Create rules
* Put events onto an event bus
* Modify event buses
* Manage targets
* Delete rules

Least-privilege IAM should be used.

---

# EventBridge and Cross-Account Events

EventBridge can be used to route events between AWS accounts.

Example:

```text
Account A
Application
    |
    ↓
EventBridge
    |
    ↓
Account B
EventBridge
    |
    ↓
Lambda / SQS
```

This is useful in multi-account architectures.

For example, separate AWS accounts may exist for:

* Development
* Testing
* Production
* Security
* Centralized monitoring

# EventBridge and Sheepeye

EventBridge could be used in a future Sheepeye architecture.

For example:

```text
Sheepeye Application
       |
       ↓
EventBridge
       |
       ├── Lambda
       ├── SQS
       └── SNS
```

A booking-related event could trigger different actions.

For example:

```text
New Booking
    ↓
EventBridge
    ↓
Rule
    ├── SQS → Background processing
    └── SNS → Notification
```

However, **you do not need to add EventBridge to Sheepeye immediately**.

Your current SNS implementation is enough. EventBridge can be added later if you want to demonstrate a more advanced event-driven architecture.

## Key Points

* EventBridge is a **serverless event bus**.
* It is used for **event-driven architectures**.
* Events are matched using **rules and event patterns**.
* Rules send matching events to **targets**.
* Common targets include Lambda, SQS, SNS and Step Functions.
* EventBridge can receive AWS service events and custom application events.
* Custom event buses can separate application event flows.
* EventBridge can route events across AWS accounts.
* EventBridge supports scheduled automation through EventBridge Scheduler.
* EventBridge can work together with SQS for event routing plus asynchronous processing.
* **EventBridge = event routing and automation.**
* **SQS = queueing, buffering and asynchronous processing.**
* **SNS = pub/sub and fan-out.**
* **CloudWatch = monitoring, metrics, logs and alarms.**
* For SAA, think of EventBridge when the requirement is **"when this event happens, automatically trigger the appropriate action."**
